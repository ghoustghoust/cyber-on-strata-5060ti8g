> **这一册解决什么**：模型"看起来在干活、其实在原地打转"的那一类 —— **重复调用同一个工具、工具名漂移、工具调用被打进思考通道后丢失**。

---

## §1 两类问题，别混为一谈

| 类 | 形态 | 谁的问题 |
|---|---|---|
| **A · 重复调用 / 原地打转** | 同一个工具、同一批参数，**原样重发**；失败不改变策略 | 模型 + 平台护栏 |
| **B · 工具调用格式坏 / 丢调用** | 调用被写进**思考通道**；工具名漂移（`conversation_read` → `Conversation_read`）；工具块泄漏成正文 | **引擎/服务侧**（我们改过）+ 采样设置 |

---

## §2 A 类：重复调用（数字来自报告原件）

- **案例**：单轮 **368 步**、**343 次确定性失败**（`todo` 幻觉 **202 次** + localhost 被 SSRF 拦 **139 次**）；另一侧 **42 次 WebFetch 只对上 9 个签名**。
- **决定性对照**（这条最值钱）：**同 harness、同 42 个工具、同 prompt** —— 换一个模型 **0 次完全重复**（撞 3 次就申请提权）；用三元件则 **200 次**（22 次审批事件 = **0**）。
  ⇒ **主因在模型侧，差异在"失败是否触发策略更新"**，不是"工具太多"。
- **四层归因**：① **触发**：环境**确定性失败**（请求本身不可能成功）→ ② **放大·模型**：原样重发 → ③ **放大·harness**：提醒阈值 `[3,5,8]`，**第 8 次之后永久静默、只提醒不阻断** → ④ **加剧·上下文**：compaction 把失败证据抹掉，于是下一轮"重新"试。

### 治法（平台侧）：Pre/Post 双时机 hook guard

| 项 | 做法 |
|---|---|
| 时机 | **Pre**（调用前拦）+ **Post**（结果回灌前改） |
| 工具名 | 白名单 + `difflib` 给最近候选（治"工具名幻觉"） |
| **熔断判据** | **「同参数 + 同失败结果」≥ 3 次** |
| 失败签名 | `sha1(结果前 300 字符去数字)` |
| 结果改写 | `decision.feedback` 把错误结果改写成**带绕行地图**的反馈（告诉它换哪条路），而不是原样回灌 |
| 阈值 | 提醒阈值**密集化**（别等第 8 次） |
| 平台约定 | `AGENTS.md` 里写**失败协议**与**本机绕行地图** |
| 自测 | 报告里 **22/22** |

## §3 B 类：调用被写进思考通道 —— **这是我们 serve 层自己修的**

**现象**：模型把 `<tool_call>` 写在 **思考（reasoning）通道里**，而不是正文通道 ⇒ 客户端只看到"想了一堆、什么都没调用"。

**我们的做法**：serve 层的增量解析器把**思考通道里合法成形的调用读成真调用**：

| 落点 | 行为 |
|---|---|
| `frontend.py` | 解析器记账：`rescued` = **从思考里救回来、按调用交付**的个数；`refused` = **留在思考里**的个数 |
| `server.py` | 收尾统计 `tool_calls_from_reasoning`，并打印一行：`[strata] tool calls inside the thinking: N read as calls, M kept as ...` |
| 规则依据 | `fixtures/rcall_specimens.json` 的 `_about`：**`calls` = 按 #1058 规则**真正交付为调用的工具名；"混合尾巴"（一个已声明的调用 + 一个未声明工具的包装调用）⇒ **交付已声明的那个，包装留在思考里** |
| 语料 | **37 条**样本：25 条来自上游 PR #525 的语料（talisp / 47Hunter47 与 review 者），12 条是 47Hunter47 找回的**实况搁浅** |
| 回归 | `test_reasoning_tools.py` · `test_reasoning_rescue.py`（随仓） |
| 相关守卫 | 调用参数**被扣住生成期间**保持 keep-alive（`#1666`）；工具集**换个顺序回来**时按首次出现的顺序稳定住（`#1624`，保住前缀缓存）；服务端**不读的内容块**（`tool_reference` / `document` / `search_result` / server tool 块 / `file` / `audio`）给日志而不是 400（`#1664`） |

**怎么看到它在工作（判据，能变红）**：服务端日志里那行 `tool calls inside the thinking: N read as calls, M kept as reasoning` ——
**N>0 说明救回来了**；把 `rcall_specimens.json` 里的样本喂进去，N 应当 = 样本标称的 `calls` 数（**这就是负控**：改坏解析器，N 会掉）。

## §4 已知边界与未验（照抄，不许当已解决读）

- **P0 只把重复压到 3 次后熔断** —— 它**不会让不可达的请求成功**。设计目标是"止血"，不是"让它跑通"。
- **桌面端装后实际效果未验**（报告自己标注）：判据是状态目录里出现会话文件与 `_invocations.log`（**文件空 = 没跑**）。
- `PreToolUse` 对**未注册的工具名未实测**。
- "三值量化 → 工具名幻觉"目前**只是假设**，没有对照实验。
- serve 侧那套 `rcall` 规则依据的是**上游 #804/#1058** 的语义；换上游版本要重新对齐。

## §5 复用的坑（报告里 7 条里最值钱的几条）

1. hook 走 PowerShell 时，**引号语法错会静默不执行** —— 得用"输出有没有内容"来判活，不能靠"没报错"。
2. hook **不受工作区沙箱 ACL 影响**（别指望沙箱拦它）。
3. 改写带 `\n` 的文件时**别把 LF 变 CRLF** —— 对 LF 敏感的 YAML 会当场坏。
4. hook 每次 **约 900–1000 ms**；嫌慢就改 Node 实现。
5. 打补丁的语法要分清：**改已有用 `- id:`，新增用 `- insert:`**。
6. **杀引擎 ≠ 杀作业**：只杀进程，循环会立刻拉起新实例（我们在另一条线上踩过，见 `docs\02`）。
